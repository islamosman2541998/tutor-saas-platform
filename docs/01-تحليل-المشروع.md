# تحليل المشروع — منصة SaaS لإدارة المدرسين والدروس الخصوصية

## 1. الـActors

| Actor | نوع الوصول | ملاحظات |
|---|---|---|
| Super Admin | مستخدم منصة، `tenant_id = null` | يدير كل الـTenants والباقات |
| Teacher Owner | مستخدم Tenant، الدور الأساسي | يمتلك الحساب بالكامل |
| Assistant | مستخدم Tenant، صلاحيات محدودة | حضور، طلاب، مجموعات |
| Accountant | مستخدم Tenant، صلاحيات مالية | دفعات، مصروفات، تقارير مالية |
| Content Manager | مستخدم Tenant، صلاحيات محتوى | إدارة الموقع التعريفي |
| Student / Guardian | زائر بدون حساب في الـMVP | يتفاعل عبر رابط QR وفورم الانضمام فقط |
| Website Visitor | زائر عام | يشاهد الموقع التعريفي ويرسل طلب انضمام |

لا يوجد تسجيل دخول للطالب أو ولي الأمر في الـMVP — التفاعل عبر روابط موقّعة (QR) وفورم عام فقط.

## 2. Use Cases الرئيسية لكل Actor

**Super Admin**: إدارة Tenants (تفعيل/إيقاف/تمديد اشتراك)، إدارة الباقات، مراقبة الاستخدام، Support Login مسجل بالـActivity Log، إدارة إعدادات المنصة العامة، مراقبة الـQueue والإيميلات الفاشلة.

**Teacher Owner**: كل شيء داخل حسابه — الإعداد الأولي (Setup Wizard)، إدارة الهيكل الأكاديمي (سنوات/مراحل/صفوف/مواد/أماكن)، المجموعات ومواعيدها، الطلاب والاشتراكات، الحصص والحضور (QR ويدوي)، المصروفات والدفعات والمتأخرات، طلبات الانضمام، الموقع التعريفي، إعدادات التصميم (Dashboard/Login/Website)، إدارة المستخدمين المساعدين وصلاحياتهم، التقارير والتصدير.

**Assistant**: حسب الصلاحيات الممنوحة — عرض/إضافة/تعديل طلاب، تسجيل حضور، إدارة مجموعات، مشاهدة مواعيد.

**Accountant**: مشاهدة مصروفات، تسجيل دفعات، طباعة إيصالات، مشاهدة متأخرات، تصدير تقارير مالية — بدون صلاحية تعديل بيانات أكاديمية.

**Content Manager**: سلايدر، نصائح، صفحات، آراء طلاب، محتوى الموقع — بدون صلاحية مالية أو أكاديمية.

**Website Visitor**: تصفح الموقع، إرسال فورم انضمام، مشاهدة النصائح والمجموعات المتاحة.

**Student (عبر QR)**: مسح QR → إدخال كود الطالب + آخر 4 أرقام هاتف → تسجيل حضور فوري بدون حساب.

## 4. قواعد العمل الحرجة (Business Rules)

### عزل الـTenant
- `tenant_id` يُشتق دائمًا من السياق الحالي (Auth User أو Domain/Slug المطابق للطلب) — لا يُقرأ أبدًا من الفورم أو الـRequest.
- كل Model خاص بـTenant يستخدم Global Scope يفلتر تلقائيًا بـ`tenant_id`.
- كل Policy تتحقق أولًا أن الـSubject ينتمي لنفس Tenant المستخدم الحالي قبل أي تحقق آخر.
- أي Foreign Key عبر نموذجين (مثال: `grade.stage_id`) يجب التحقق أن الاثنين لنفس Tenant عبر Validation Rule مخصص، وليس فقط عبر قيود قاعدة البيانات.

### الهيكل الأكاديمي
- عام دراسي واحد فقط `is_current = true` لكل Tenant في نفس الوقت (يُفرض داخل Transaction عند التفعيل: تعطيل القديم ثم تفعيل الجديد).
- لا حذف نهائي لسنة دراسية أو بيانات مرتبطة بها؛ فقط `closed` / `archived`.
- حذف مرحلة/صف/مادة/مكان يُمنع إذا وُجدت مجموعات أو بيانات مرتبطة — تحذير عربي واضح بدل خطأ تقني.

### المجموعات والاشتراكات
- الطالب يرتبط بالمادة **فقط** من خلال `Enrollment` في مجموعة — لا علاقة مباشرة Student↔Subject.
- لا يمكن وجود أكثر من `Enrollment` بحالة `active` لنفس (`student_id` + `group_id`) في نفس الوقت — يُفرض بفحص داخل Transaction عند الإنشاء (وليس Unique Index وحده، لأن السجلات التاريخية يجب أن تبقى).
- عند امتلاء المجموعة (`current_students_count >= capacity`) يُحوَّل أي طلب اشتراك جديد تلقائيًا إلى `WaitingListEntry` بدل رفضه.
- `current_students_count` قيمة **مشتقة** (Query عبر `withCount`)، وليست عمودًا مخزّنًا يمكن أن يتعارض مع الواقع.
- تعديل سعر مجموعة لا يغيّر الاستحقاقات المولّدة مسبقًا؛ يؤثر فقط على التوليد المستقبلي.

### الحصص والحضور
- QR ديناميكي لكل حصة فقط، له `token` عشوائي طويل، `expires_at`، وحالة `is_active` — لا يوجد QR ثابت للمدرس أو للمجموعة.
- إعادة توليد QR تُلغي الـtoken السابق فورًا (تحديثه بدل الاحتفاظ به فعالًا).
- تسجيل الحضور عبر QR يتطلب سلسلة تحقق كاملة بالترتيب: صلاحية الرابط → صلاحية الوقت → حالة الحصة `open` → حالة QR `active` → انتماء الطالب لنفس Tenant → وجود Enrollment نشط في نفس المجموعة → عدم وجود سجل حضور سابق لنفس الحصة → صحة كود الطالب → صحة آخر 4 أرقام الهاتف (إن كانت مفعّلة).
- `attendance_records` له Unique Index على (`class_session_id`, `student_id`) لمنع التكرار على مستوى قاعدة البيانات كخط دفاع أخير، بالإضافة للتحقق التطبيقي.
- بعد قفل الحصة (`attendance_is_locked`) أي تعديل يتطلب صلاحية خاصة ويُسجَّل في Activity Log إجباريًا.
- Rate Limiting على محاولات إدخال كود الطالب لمنع التخمين، بدون كشف أي معلومة عن صحة الكود جزئيًا.

### المالية
- المبالغ المالية `decimal(10,2)` دائمًا — ممنوع استخدام `float`.
- التسلسل الإجباري: `Student → Enrollment → MonthlyDue → Payments` — لا حقل Boolean للدفع على مستوى الطالب.
- توليد الاستحقاقات الشهرية عملية **Idempotent**: Unique Index على (`enrollment_id`, `billing_year`, `billing_month`) يمنع التكرار حتى لو أُعيد تشغيل الـJob.
- لا يُنشأ استحقاق قبل `enrollment.joined_at` ولا بعد `enrollment.left_at`/تاريخ الانسحاب.
- كل عملية دفع أو إلغاء دفع تُنفَّذ داخل Database Transaction: تحديث `paid_amount`/`remaining_amount`/`status` على `MonthlyDue` بشكل ذري مع إنشاء الدفعة.
- ممنوع دفع بقيمة صفر أو سالبة، وممنوع تجاوز `remaining_amount` إلا عبر مسار "رصيد مقدّم" الصريح.
- لا حذف نهائي للدفعات أو الاستحقاقات المرتبطة بدفعات — فقط `cancelled`/`refunded` مع سبب إجباري وتسجيل Activity Log.
- الطالب "متأخر" منطقيًا إذا: `due_date < today` و `remaining_amount > 0` و `status ∈ {unpaid, partially_paid}` — هذا Query محسوب، وليس حالة مخزنة يجب تحديثها يدويًا.

### الاشتراك في المنصة (Subscription)
- انتهاء اشتراك المدرس **لا يحذف بيانات** — فقط يمنع عمليات الإنشاء الجديدة (طلاب/مجموعات جدد) عبر Middleware، مع السماح بالقراءة والتجديد.
- تجاوز حدود الباقة (`max_students`, `max_groups`, ...) يُمنع بأخطاء 4xx عربية واضحة مع رابط ترقية، وليس خطأ 500.

### عام
- Soft Deletes على كل البيانات الإدارية القابلة للحذف (طلاب، مجموعات، أماكن، مواد، مراحل، صفوف، محتوى الموقع). لا Soft Delete على السجلات المالية والحضور — تُستخدم حالات (`cancelled`, `archived`) بدلًا من الحذف.
- كل عملية حساسة (مالية، حضور، صلاحيات، إعدادات، Support Login) تُسجَّل في `activity_log` مع `old_values`/`new_values`.

## 5. الحالات الخاصة (Edge Cases) الواجب معالجتها

1. طالبان بنفس الاسم ونفس رقم الهاتف داخل نفس Tenant → تحذير تكرار وليس منع تلقائي.
2. مجموعة وصلت للسعة الكاملة أثناء محاولة اشتراك طالبين في نفس اللحظة (Race Condition) → استخدام Lock/Transaction عند فحص السعة قبل إنشاء Enrollment.
3. إعادة تشغيل Job توليد الاستحقاقات الشهرية أكثر من مرة لنفس الشهر → لا تكرار (Unique Index + فحص مسبق).
4. طالب انسحب من مجموعة في منتصف الشهر → لا يُنشأ استحقاق للشهر التالي، والاستحقاق الحالي يبقى كما هو (لا استرجاع تلقائي جزئي إلا يدويًا).
5. تعديل سعر مجموعة بعد توليد استحقاقات — يجب ألا تتأثر الاستحقاقات القديمة.
6. مسح QR بعد انتهاء صلاحيته مباشرة (Race قريب من `expires_at`) → التحقق من الوقت يتم على السيرفر وقت الإرسال الفعلي وليس وقت تحميل الصفحة.
7. طالب بلا رقم هاتف مسجَّل يحاول تسجيل حضور QR → بديل PIN خاص يصدره المدرس، أو تسجيل يدوي فقط.
8. تعارض مواعيد بين مجموعتين لنفس المكان أو نفس المدرس → تحذير عند الحفظ وليس منع صارم (قد يكون مقصودًا مع Assistant آخر).
9. إغلاق حصة بها حضور غير مكتمل التسجيل → يجب تأكيد صريح (SweetAlert) قبل اعتبار غير المحددين غائبين.
10. Super Admin يسجّل دخولًا مؤقتًا لحساب مدرس (Support Login) → جلسة محددة المدة، صلاحيات كاملة داخل الـTenant، تسجيل إجباري في Activity Log عند البداية والنهاية.
11. انتهاء اشتراك المدرس بينما لديه حصة مفتوحة (QR نشط) → يُسمح بإغلاق الحصة الحالية لكن يُمنع فتح حصة جديدة.
12. حذف مرحلة/مادة مرتبطة ببيانات موجودة → منع مع رسالة توضح عدد السجلات المرتبطة.
13. تحويل طلب انضمام (Join Request) إلى طالب موجود بالفعل (تكرار) → عرض تحذير تطابق قبل الإنشاء.
14. مستخدم Assistant تمت إزالة صلاحياته بينما لديه صفحة مفتوحة → يجب أن تُطبَّق الصلاحيات على مستوى Middleware/Policy في كل طلب، وليس فقط عند تحميل الصفحة.
15. تصدير Excel لعدد ضخم من السجلات → يُنفَّذ كـQueued Job مع إشعار عند الاكتمال، وليس بشكل متزامن يُجمّد الطلب.
16. رفع صورة بامتداد غير صالح أو حجم كبير أو اسم يحتوي مسارات (`../`) → فحص MIME + الحجم + توليد اسم عشوائي دائمًا.
17. نسخ مجموعات من عام دراسي سابق إلى عام جديد → نسخ بيانات المجموعة والمواعيد فقط، بدون نسخ الحضور أو المدفوعات أو الطلاب المسجَّلين تلقائيًا.
